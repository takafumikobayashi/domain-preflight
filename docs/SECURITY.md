# セキュリティ・安全設計

## 1. 最優先の制約

**MVPは診断専用（読み取り専用）であり、対象の設定を変更しない。**

- DNS変更、Access削除、WAFルール編集、HSTS設定、DMARC変更、デプロイを実行しない。
- `cf` CLIのコマンド実行は、レビュー済みの読み取り専用許可リストに限定する。
- 「dry-runがあるはず」という推測に依存しない。CLIのサブコマンドごとに権限と副作用を確認する。
- AIエージェントが提案できる変更も、MVPは**説明だけ**。自動適用しない。

## 2. 扱ってよい情報

- 公開DNSレコード、証明書、HTTPレスポンスヘッダー
- ユーザーが認証したアカウント内の、診断に必要なCloudflare設定
- 検査日時、対象ドメイン、確認できた所見

**出力してはいけない情報（例）:** APIトークン、認証Cookie、秘密鍵、環境変数の秘密値、Access認証情報、メール認証の秘密情報、非公開のリソースIDの不用意な公開。

Cloudflare連携の設定出力には、公開情報と非公開の管理情報が混在し得る。レポートへ渡す前に最小化・マスキングする。

## 3. 対象指定・ネットワーク安全性

- 入力はDNSホスト名として検証し、`file://`、任意URL、ユーザー指定ポート、IPリテラルは初期版で受け付けない。
- 内部IP、リンクローカル、ループバック、メタデータサービス向けアドレスに接続しない（`src/net/address.ts`。IPv4射影アドレス `::ffff:a.b.c.d` はIPv4部分で判定する）。
- DNSリバインディングに備え、接続先の各解決結果・リダイレクト先を検証する。
- リダイレクト回数、レスポンスサイズ、接続タイムアウト、並列数に上限を設ける。
- HTTP検査は少数の安全なリクエストに限定し、探索的クロールや脆弱性攻撃を行わない。
- 診断対象は自分が管理するサイト、または点検を許可されたサイトを基本とする。

## 4. Cloudflare認証と権限

- ログイン操作は利用者の端末で行う。ツールが資格情報を収集しない。
- `cf auth login`（OAuth）のトークンは書き込み権限を持つ。コマンドの許可リストは「ツールが呼ぶもの」を絞るだけで、トークンの権限は小さくならない。そのため、Zone / DNS / Zone Settings の **Read だけを持つ API トークン**の利用を推奨する。
- 名前が読み取り系に見えても副作用のあるコマンドがある（例: `cf dns records scan` はスキャンを開始する）。許可リストはサブコマンド単位で、`--help` と `--dry-run` で確認してから登録する。
- 可能なら対象ゾーン限定、読み取り専用の最小権限を使用する。
- CLI呼び出しにはシェル展開を使わず、実行ファイル・引数を固定してインジェクションを防ぐ。
- `cf`の標準エラーや例外をそのまま外部に公開せず、機密文字列を除去する。
- 権限が不足する場合、確認できない事項を`not_checked`または`error`として説明する。

## 5. 誤った改善提案を防ぐ

- **HSTS:** 初回から長い`max-age`、`includeSubDomains`、preloadを一律に勧めない。全サブドメインのHTTPS対応と運用を考慮。
- **メール送信しないドメイン:** Null MX / SPF `-all` / DMARC `p=reject`の提案は、用途が確認できた場合のみ。送信や受信が必要なドメインには適用しない。
- **DMARC:** `p=reject`の採用前に正規の送信元のSPF・DKIMの整合性を確認する必要がある。
- **DNSSEC:** レジストラのDS設定とDNS側の鍵管理に依存する。未設定を機械的な事故扱いにしない。
- **Proxy:** CloudflareのDNS-onlyレコードにはCloudflareのHTTP設定が直接適用されない。外部サービスとの互換性を確認する。
- **Strict TLS:** ゾーンのSSL/TLSモードと、外部から観測する証明書の状態を混同しない。

## 6. データ取り扱い

- デフォルトで匿名テレメトリも含めて送信しない。
- DNSの問い合わせは、利用者のシステムのリゾルバ（または `--resolver` で指定した先）にドメイン名を送る。DoH（DNS over HTTPS）でDNSSECを確認する機能を追加する場合は、ドメイン名が第三者のDoH事業者へ送られるため、明示的なオプトインにする。
- レポートはローカルに保存できるが、内部設定を含む場合はGitHubへそのまま公開しないように警告する。
- 例示には`example.com`等の架空または予約済みドメインを使用する。
- テストではモック・フィクスチャを使い、実アカウントの設定変更や課金操作を行わない。

## 7. 将来の変更支援フェーズ（MVP対象外）

将来的に設定変更を実装する場合は、最低限以下を満たしてから検討する。

1. 対象・変更内容・影響範囲を明示する。
2. 変更前のバックアップ／スナップショットを取る。
3. dry-run、差分、依存関係・メール影響を確認する。
4. 人間による明示承認を得る。
5. 変更後に独立した方法で検証する。
6. ロールバック手順・監査ログを残す。

本ツールはセキュリティを保証しない。問題が見つからなくても、それは**検査した範囲で所見がない**という意味に限る。
