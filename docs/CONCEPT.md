# コンセプト — Domain Preflight

> v0.2（2026-11-22）: 利用者の想定を「設定に詳しい開発者」から「Webサイトを作ったが、公開・移行・運用に不安がある人」へ見直した。v0.1 からの変更点は末尾に記す。

## 1. 一文で表すと

**Webサイトを作った。その後は大丈夫？**

Domain Preflight は、Webサイトの公開・移行・運用に必要な設定を確認し、専門知識がなくても問題点と改善方法を理解できるようにするオープンソースツール。DNS、HTTPS、メール、セキュリティ設定など、サイト運営で見落としやすい項目を点検する。AI エージェントと連携し、安全な改善を支援する。

英語のメッセージ: **Know your site. Secure your setup.**

「Preflight」は航空機の飛行前点検を意味する。公開前の確認、移行の前後、運用中の定期点検に使う。

## 2. 誰を助けるか

### 中心に置く利用者

**CMS（WordPress など）でサイトを運用してきて、AI の力を借りて別の構成へ移ろうとしている個人・小規模事業者・地域団体。**

- 記事の編集や画像のアップロードはできるが、DNS、TLS、CDN、デプロイの仕組みはレンタルサーバーや CMS が肩代わりしてくれていた。
- Claude Code などの AI でサイトを作り直すことはできる。つまずくのは、その後の「今のドメインのまま公開する」「メールを止めない」「検索からの流入を失わない」といった部分。
- 専門用語を知らないので、何を聞けばよいかも分からない。

### 同じ仕組みで助けられる人

- AI で初めて Web サイトを作った人
- 既存サイトを保守している制作・保守担当者
- 地域団体などで、引き継いだサイトを運用している人

### 利用者に合わせた届け方

| 段階 | 届け方 | 利用者の操作 |
| --- | --- | --- |
| 今 | Claude Code プラグイン（Skill + CLI） | AI に「サイトを移したい」「メールが届くか心配」と普段の言葉で話す。用語の翻訳と質問は AI が担う |
| 今 | CLI 単体 | 制作者・開発者が直接使う。CI にも組み込める |
| 将来 | Web 画面 | ドメイン名を入れるだけ。公開情報の点検に限る |

**AI が窓口になる**のが前提。ただし、説明の中身（何を確認したか、なぜ大事か、放っておくと何が起きるか）はツールの出力に固定で持たせ、AI の言い換えに任せない。

## 3. 解決したい課題

サイトを作ることより、その後の公開・移行・運用に壁がある。

| 利用者がしたいこと | 実際に必要になる知識 |
| --- | --- |
| 今のドメインをそのまま使いたい | DNS、NS、CNAME、A レコード |
| HTTPS で安全に公開したい | TLS 証明書、HTTPS への転送、HSTS |
| 問い合わせのメールを止めたくない | MX、SPF、DKIM、DMARC |
| Google 検索から来る人を失いたくない | 301 リダイレクト、canonical、sitemap |
| 問い合わせフォームを動かしたい | フォームの送信先、外部サービス |
| 安全に運用し続けたい | 設定の点検、不要な設定の整理 |

特に移行では、次のような事故が起きやすい。

- レンタルサーバーのメールを使っていて、MX がサイトと同じサーバーを指している。サイトを移すために A レコードを変えたり、サーバーを解約したりすると、**メールも止まる**。
- 旧サイトの URL が新サイトにないまま公開し、検索や外部のリンクから来た人が 404 になる。
- DNS 移行でウェブ以外のレコード（メールの認証、サービスの所有確認）を写し忘れる。
- 「設定されている」ことと「正しく機能している」ことを取り違える。

## 4. 提供価値の中心

利用者が本当に知りたいのは「どの設定が危険か」ではなく、次の3つ。

1. **自分のサイトは今のままで大丈夫か**
2. **何をすればよいか**
3. **設定を変えても壊れないか**

これに答えるために、

- **事実と不確かさを分ける**: 確認できたこと、問題、状況次第のこと、確認していないことを区別する。「未確認」を「大丈夫」と言わない。
- **やさしい説明を付ける**: 各項目に、何を確認したか・なぜ大事か・放っておくと何が起きるかを、用語に頼らずに書く。
- **目的ごとに答える**: 総合点ではなく、「Webサイトの公開」「メール」などの目的ごとに、確認が必要な項目の数を示す。
- **用途に合わせて提案する**: メールを使うかどうかを確かめずに、メールを止めかねない設定を勧めない。
- **変える前に確かめる**: 自動で直さない。改善の手順、影響、確かめ方、元に戻し方を示す。

診断項目を増やすより、少ない項目を丁寧に説明することを優先する。

## 5. 3つの使い方

| 使い方 | いつ | 何を確かめるか |
| --- | --- | --- |
| **Site Check** | 公開中のサイトを点検したいとき | DNS、HTTPS、証明書、メール認証、基本的なセキュリティ設定 |
| **Migration Preflight** | 移行する前 | 今の DNS・メール・主要 URL を記録し、移行で壊れやすい点（メールの同居など）を洗い出す |
| **Post-Migration Check** | 移行した後 | 記録と比べ、サイト・URL・メールが失われていないかを確かめる |

コマンドとしては `check`（点検）、`snapshot`（記録）、`compare`（比較）の組み合わせで実現する。

## 6. やらないこと

- Web サイトの変換・移行そのもの（WordPress から静的サイトへの変換などは、サイト構築ツールの役割）
- 設定の自動変更（HSTS の有効化、DNS レコードの削除、DMARC の強化など）
- 「WordPress から移るべきか」の断定（判断材料は示すが、更新頻度や機能によっては CMS を使い続ける方が良い場合もある）
- 安全の保証、総合点での「安全／危険」の断定
- 侵入テスト、脆弱性スキャン、大量のリクエスト
- 利用者の設定や秘密情報を外部へ勝手に送ること
- Cloudflare だけに依存すること

## 7. 既存ツールとの違い

一般的な診断ツールは「どの設定が危険か」を教える。Domain Preflight は、

- 利用者の目的（公開・移行・運用）と用途（メールを使うか）に合わせて、
- 確認できたことと確認できなかったことを分けて、
- 専門用語を知らない人にも分かる言葉で、次に何をすればよいかを示す。

判定は CLI に置き、AI は質問・説明・手順の案内を担う。

## 8. 成功の定義

- 専門用語を知らない人が、AI に普段の言葉で相談するだけで、自分のサイトの状態と次の一歩が分かる。
- 移行の前後で、メールが止まる・URL が消えるといった事故を、切り替える前に見つけられる。
- 出力には事実・根拠・やさしい説明・改善の候補・注意事項が含まれ、制作者や詳しい人と共有できる。
- どの処理も、対象サービスの設定を変更せずに終わる。

## 背景について

CMS から他の構成へ移る動きの背景（利用率の推移、脆弱性の報道など）を文書に書く場合は、出典を確認してから引用する。特定の出来事を移行の原因と断定しない。WordPress 自体が一律に危険なわけではなく、更新と管理が重要である。

## v0.1 からの変更点

| 項目 | v0.1 | v0.2 |
| --- | --- | --- |
| 中心の利用者 | 個人開発者、保守担当者、AI エージェント利用者 | CMS から移る個人・小規模事業者（AI が窓口）。開発者は同じ仕組みで支援 |
| 中心の課題 | DNS・HTTPS・セキュリティ設定の点検 | 公開・移行・運用で壊さないこと |
| 優先する機能 | Cloudflare 内部設定の照合 | やさしい説明、目的ごとの準備状況、移行の前後チェック（Cloudflare 連携は後） |
| 説明 | 用語中心 | 何を確認したか・なぜ大事か・放っておくと何が起きるか |
